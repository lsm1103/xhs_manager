## 2. 规格边界

| 规格 | 核心责任 |
|---|---|
| 核心领域与工作流 | 标识、状态机、工作项、事务、幂等、审计 |
| 研究流水线 | 来源采集、标准化、去重、聚类、证据包 |
| 选题引擎 | 候选生成、评分、版本、选题审批前数据 |
| 内容生成 | 标题、正文、视觉脚本、图片、内容版本 |
| 审核与审批 | 自动检查、选题审批、发布审批、版本失效 |
| 发布 | 排期、浏览器准备、提交、结果核验、恢复 |
| 评论运营 | 采集、分类、风险、限流、回复、熔断 |
| 数据分析 | 指标快照、实验、单篇复盘、周复盘 |
| 飞书集成 | 回调、鉴权、卡片、命令、文档归档 |
| 知识库 | 问题库、知识条目、生命周期、检索 |
| 运维与安全 | 配置、密钥、健康、日志、备份、告警 |
| 账号策略 | 目标用户、人格、内容支柱、红线和策略版本 |
| 需求追踪 | 产品需求到规格和验收条件的映射 |

## 3. 通用约定

### 3.1 标识

- 内部主键统一使用字符串型全局唯一标识。
- 外部平台标识单独保存，不作为内部主键。
- 所有命令包含 `command_id`。
- 所有外部副作用包含 `idempotency_key`。
- 所有异步流程包含 `workflow_id` 和 `task_id`。

### 3.2 时间

- 数据库存储协调世界时。
- 时间字段使用带时区的国际标准时间字符串。
- 展示和排期使用账号配置时区。
- 所有表至少包含 `created_at`。
- 可修改记录包含 `updated_at`。

### 3.3 版本

- 账号策略、提示词、选题、内容、审批对象和回复均显式版本化。
- 版本发布后不可原地修改。
- 任何影响发布内容的修改都创建新内容版本。
- 审批只对绑定版本有效。

### 3.4 状态返回

通用命令结果：

```json
{
  "command_id": "唯一标识",
  "accepted": true,
  "resource_type": "content_task",
  "resource_id": "唯一标识",
  "current_state": "researching",
  "message": "已受理"
}
```

通用错误：

```json
{
  "error": {
    "code": "APPROVAL_VERSION_MISMATCH",
    "message": "审批绑定的内容版本已经失效",
    "retryable": false,
    "action": "请打开最新审批卡片"
  }
}
```

### 3.5 错误类别

| 类别 | 是否自动重试 | 处理 |
|---|---|---|
| 临时外部错误 | 一次 | 延迟后使用相同幂等键重试 |
| 结构输出错误 | 一次 | 修复或重新调用 |
| 输入不足 | 否 | 补充资料或人工处理 |
| 非法状态 | 否 | 拒绝并审计 |
| 审批失效 | 否 | 创建新审批 |
| 平台风控 | 否 | 熔断并人工恢复 |
| 结果未知 | 否 | 先核验外部状态 |
| 永久权限错误 | 否 | 停止并告警 |

### 3.6 审计

以下行为必须写审计日志：

- 策略变更；
- 审批；
- 暂停和恢复；
- 发布；
- 评论回复；
- 手动接管；
- 数据导出；
- 密钥配置状态变化；
- 知识状态变更。

审计只保存必要摘要，不保存明文密钥和完整会话。

## 4. 需求追踪规则

- 每份规格必须列出覆盖的产品需求编号。
- 每条验收条件使用 `AC-<规格编号>-<序号>`。
- 每个实现任务必须指向至少一条验收条件。
- 产品需求变化时，先更新产品需求文档，再更新规格。
- 规格与产品需求冲突时，以产品需求文档为准。

## 5. 完成定义

某一规格视为实现完成，必须同时满足：

1. 数据迁移已提交；
2. 领域规则有单元测试；
3. 外部适配器有契约测试；
4. 错误路径已验证；
5. 审计和日志已覆盖；
6. 需求编号可以追踪到测试；
7. 不含明文密钥或未脱敏个人信息；
8. 文档中的验收条件全部通过。
