# 视频工厂控制台 · 系统设计

> 目标读者：你自己（单人、本机、macOS）
> 状态：设计稿，待拍板后动工
> 相关：[video-pipeline-design.md](video-pipeline-design.md)（流水线本身的设计）

## 0. 一句话结论

**不要做一个"全功能后台"，做一个"看得见 + 能重跑"的控制台。**

这个项目真正缺的不是管理功能，而是三件事：一次运行到底发生了什么（现在只能翻日志）、
外部工具此刻是死是活（现在要挨个手查）、产物在哪（现在埋在 uuid 目录里）。
把这三件事做掉，大约是两天的工作量；剩下的"管理"能力大部分已经在 CLI 里了，
控制台只需要把它们暴露成按钮，而不是重写一遍。

## 1. 这个项目现在到底有什么

三块东西，彼此独立，成熟度差别很大。

### A. 视频工厂 `video_pipeline` — 能力最全，**完全没有界面**

六个阶段，每个阶段都能单独跑、能续跑、失败能定位到阶段：

```
collecting → selecting → materializing → composing → rendering → publishing
  采集         选题脚本      素材配音        HTML组合      逐帧渲染      发布
```

| 子系统 | 现状 | 可视化价值 |
|---|---|---|
| 采集 | 13 个平台，每个是一条后端链（站内 API → 登录态 → 站外索引），自动降级 | **高**：哪个平台在降级、为什么降级，现在只能看日志 |
| 选题 + 脚本 | Claude API 生成，或 `seed --script` 喂手写 JSON | 中：脚本是 JSON，需要可读的预览 |
| 素材 | MoneyPrinterTurbo(Pexels) 逐场景搜 + **人脸检测过滤**（肖像权红线）+ 文字卡兜底 | **高**：被剔除的素材和原因现在只在日志里闪一下 |
| 配音 | TTS 抽象层（edge / voxcpm / studio），逐场景合成 + 句级时间标记对齐 | 中：需要能试听每个场景 |
| 配乐 | 62 首曲库，6 种情绪，按库内百分位选曲 | 低 |
| 版面 | 7 种 layout × 3 套主题 × 10 种转场，`--t` 驱动的确定性 HTML | **高**：改 CSS 时没有回归对照 |
| 渲染 | Playwright 逐帧截图 + ffmpeg，封面按平台比例单独排版 | 中：耗时最长，最需要进度可见 |
| 发布 | 小红书 Playwright 持久化 profile，draft / publish 两种模式 | 中 |
| 调度 | 每日定时 + cron/launchd 配置生成 | 低 |

数据落在 8 张表：`video_pipeline_runs / trend_signals / topics / scripts /
materials / compositions / renders / publications`。
**这 8 张表现在只能用 sqlite3 或手写 Python 查。**

现有入口只有 CLI 11 个子命令：
`run stage status seed schedule schedule-config xhs-login xhs-check site-login collect-doctor config`

### B. 内容运营主系统 — **REST API 齐全，没有界面**

`accounts / research runs / evidence packages / topic proposals / content versions /
publication plans / tasks / approvals / audit logs` 共 20 张表，26 个 API 端点，
带任务队列（`queue.py` + `worker.py`）和飞书审批回调。

这是另一条产品线（图文内容运营），和视频工厂目前**没有打通**。
本设计**不把它纳入第一期**——理由见第 6 节。

### C. TTS Studio — **已经有界面**，端口 8420

独立 FastAPI + 静态页（`index.html` 103 行 + `app.js` 237 行 + `style.css` 63 行）。
模型加载/卸载、生成试听、历史、参考音色上传、A/B 对比。

**它是本项目 UI 的既有范式：FastAPI 直接挂静态文件，vanilla JS，零构建步骤。**
控制台应该沿用，而不是另起一套前端工程。

## 2. 真实痛点（来自实际使用，不是假想）

这些是做上一支视频的过程中真实付出的成本：

1. **查库全靠一次性脚本。** 想知道"这次采到了什么"、"素材是不是重复了"、
   "场景时长有没有落库"，写了十几段临时 Python。这些查询是高频且固定的。
2. **音画错位查了很久才定位。** 根因是"校准后的时长没写进库"——
   如果有一个页面并排显示「脚本声明时长 / 实际语音时长 / 组合里的场景起点」，
   一眼就能看出 195 ≠ 168。
3. **工具健康度分散在五个地方。** opencli 扩展（`opencli doctor`）、
   TTS Studio（curl 8420）、MoneyPrinterTurbo（看路径）、ffmpeg（看能力）、
   Chrome profile（看目录）、人脸模型（看是否下载）、搜索引擎是否被风控（跑一次才知道）。
   出问题时要挨个手查。
4. **产物找不到。** 成片、封面、旁白分段、字幕、`composition/index.html`
   都在 `data/video_pipeline/<run-uuid>/<script-uuid>/` 下，只能靠 `ls` 翻。
5. **改一个参数要重跑整条链。** 想把语速从 +25% 调回 +10% 看看效果，
   得手动清库、删文件、重跑三个阶段。

**结论：控制台的第一价值是"看"，第二价值是"重跑某一步"，"新建"排最后。**

## 3. 信息架构：6 个页面

### 3.1 总览 `/`

- 最近 20 次 run：日期、当前阶段、各阶段耗时条、热点/选题/视频/发布计数
- 卡住或失败的 run 置顶，直接显示失败阶段和错误摘要
- 右上角一行工具状态灯（详见 3.6），红了可点进去

数据来源：`video_pipeline_runs` + 各阶段表的 count

### 3.2 运行详情 `/run/{id}` ← **最重要的一页**

纵向阶段时间轴，每个阶段展开后是它自己的产物：

| 阶段 | 展开内容 |
|---|---|
| 采集 | 各平台的 backend / status / notes（降级原因）、入库条数、去重数 |
| 选题 | 选题标题、角度、评分、引用了哪几条信号 |
| 脚本 | **逐场景表格**：layout / 声明时长 / 实际语音时长 / 旁白 / 屏幕文字 / 素材关键词 |
| 素材 | 每个场景的素材缩略图 + 来源 + **被肖像权剔除的条目和原因** |
| 组合 | `index.html` 直接嵌 iframe，带一条时间轴滑块（调用页面里现成的 `window.__seek(t)`） |
| 渲染 | 成片内嵌播放、封面各比例预览、渲染耗时、文件大小 |
| 发布 | 各平台标题/正文/标签、发布状态、外链 |

**一致性校验条**（这一条直接对应痛点 2）：
并排显示「脚本总时长 / 语音总时长 / 组合总时长 / 成片总时长」，
四个数字对不上就标红。

### 3.3 采集信号 `/signals`

- 按 run / 平台 / 关键词筛选，按热度分或**发布时间**排序
- 每条显示：标题、作者、点赞/评论、发布时间、**距今天数**、后端来源（站内/索引）
- 一眼能看出"这条是 434 天前的"——这正是上一轮才补上的字段

数据来源：`video_trend_signals`

### 3.4 素材与产物 `/assets`

按 run/script 分组的文件浏览器：成片、封面、逐场景素材、旁白分段、BGM、字幕。
支持直接播放/预览，以及"在 Finder 中显示"。
**这一页的存在意义就是让人不用再 `cd` 到 uuid 目录。**

### 3.5 版面模版 `/templates`

7 种 layout × 3 套主题的实时预览，复用现有的
`composition/preview.py`（它已经能用样例脚本生成全版面 HTML）。
带时间滑块，可以看动画在任意时刻的状态。
**用途：改 CSS 时的回归对照。**

### 3.6 工具体检 `/tools`

一页把所有外部依赖探测一遍，每项显示状态 + 版本 + 修复建议：

| 检查项 | 探测方式 | 已有实现 |
|---|---|---|
| 采集后端链（13 平台） | `probe_platform()` | ✅ `collect-doctor` 已实现 |
| opencli 扩展 | `opencli doctor` | ✅ |
| 搜索引擎是否被风控 | `_SEARCH_STATE` | ✅ 本轮新增 |
| TTS 提供方 | `registry.build_providers()` + available() | ✅ |
| TTS Studio 服务 | HTTP 8420 | ✅ |
| MoneyPrinterTurbo | 路径 + config.toml 里的 pexels key | ✅ |
| ffmpeg / ffprobe | 能力探测（非文件存在性） | ✅ |
| Chrome profile 登录态 | `xhs-check` / `site-login` 状态 | ✅ |
| 人脸检测模型 | `portrait_guard.available()` | ✅ |
| BGM 曲库 | 曲目数 + 索引是否过期 | ✅ |

**注意：这一页几乎不用写新逻辑，全是把已有的探测函数并联起来。**

## 4. 技术方案

### 4.1 选型：抄 TTS Studio 的作业

```
src/xhs_manager/console/
├── app.py          # FastAPI，只读 API + 白名单动作
├── queries.py      # 所有 SQL 查询集中在这里（就是把临时脚本固化）
├── probes.py       # 工具体检，聚合已有探测函数
└── static/
    ├── index.html  # 单页，顶部 tab 切换
    ├── app.js      # vanilla JS，fetch + 模板字符串
    └── style.css
```

**不引入 npm / 构建 / 框架。** 理由：
TTS Studio 用 403 行 vanilla 代码做出了可用界面；
这个控制台的交互复杂度不高于它；引入 Vite + React 会增加一个必须维护的构建链，
而它带来的收益（组件复用、状态管理）在 6 个页面的规模上收不回成本。

### 4.2 进程与端口

| 服务 | 端口 | 说明 |
|---|---|---|
| 主业务 API | 8000 | 已有，对外，带 token 鉴权 |
| TTS Studio | 8420 | 已有，模型常驻，独立生命周期 |
| **控制台** | **8500** | 新增，只绑 `127.0.0.1` |

独立进程而不是挂进 `api.py`：主 API 是业务接口，有鉴权和审计；
控制台是本机运维视图，两者的生命周期和风险等级不同，混在一起反而麻烦。
控制台**不要求** TTS Studio 在线——探测不到就在体检页标灰。

### 4.3 鉴权

只绑 `127.0.0.1`，第一期不做鉴权。
预留 `XHS_CONSOLE_TOKEN`：设了就校验 header，没设就放行。
**绝不允许绑 0.0.0.0**——这个界面能触发渲染、能看到小红书登录态目录。

### 4.4 API 草案

只读：

```
GET  /api/runs                     最近运行列表
GET  /api/runs/{id}                运行详情（含各阶段汇总）
GET  /api/runs/{id}/scenes         逐场景表（脚本+素材+语音时长）
GET  /api/runs/{id}/consistency    四个总时长的一致性校验
GET  /api/signals                  采集信号（筛选/排序/分页）
GET  /api/assets/{run}/{script}    产物清单
GET  /api/file?path=...            产物流式返回（路径白名单：仅 output_base_dir 下）
GET  /api/tools                    工具体检
GET  /api/templates                版面预览（生成临时 HTML）
```

白名单动作（第二期，全部复用 CLI 已有函数，不另写逻辑）：

```
POST /api/runs/{id}/stages/{stage}/rerun    重跑某阶段
POST /api/runs/{id}/rerender                仅重渲（改主题/语速后）
POST /api/reveal                            在 Finder 中显示产物目录
```

**写操作必须是"调用与 CLI 同一个函数"，不能在控制台里复制一份流程逻辑**——
否则 CLI 和界面会各跑各的，这是最容易腐烂的地方。

### 4.5 长任务怎么处理

渲染一支 2 分半的片子要 4 分钟左右，HTTP 请求扛不住。
第二期加动作时的做法：`POST` 立刻返回 `task_id`，
起 `subprocess` 跑 CLI，stdout 落到日志文件，
前端轮询 `GET /api/tasks/{id}`（进度直接从渲染器已有的"截帧 n/N"日志行里解析）。

**不要为此引入 Celery/Redis。** 单人单机，subprocess + 日志文件足够。

## 5. 分期

| 期 | 内容 | 产出 | 估时 |
|---|---|---|---|
| **P0** | 总览 + 运行详情 + 一致性校验条 | 能看懂任意一次 run 发生了什么 | ~1 天 |
| **P1** | 工具体检页 | 一页看清所有外部依赖死活 | ~0.5 天 |
| **P2** | 采集信号浏览器 + 产物浏览器 | 不用再写临时 SQL、不用再 cd uuid 目录 | ~0.5 天 |
| **P3** | 版面模版预览 | 改 CSS 有回归对照 | ~0.5 天 |
| **P4** | 白名单动作（重跑/重渲）+ 任务进度 | 从"看"到"管" | ~1 天 |

P0 + P1 就已经解决了第 2 节里 5 个痛点中的 3 个。建议先做这两期再决定要不要往下。

## 6. 明确不做的

- **不做多用户、权限、云端部署。** 单人本机，数据是 SQLite，浏览器登录态在本地 profile。
- **不把内容运营主系统（20 张表）搬进来。** 那是另一条产品线，它已经有完整 REST API，
  真要做界面应该单独做。两条线现在没打通，硬塞进一个控制台只会让两边都难用。
- **不做视频剪辑器。** "剪辑"在这个项目里等于"改脚本 JSON + 重跑 composing"，
  做时间轴拖拽编辑器是另一个量级的工程，收益远小于把现有流程看清楚。
  第一期给到"脚本 JSON 在线编辑 + 保存后重跑"就够了。
- **不做实时协作、通知中心。** 飞书审批已经在主系统里了，不重复建设。

## 7. 需要你拍板的三件事

1. **第一期只读，还是直接带上"重跑"按钮？**
   我建议只读（P0+P1），因为写操作要处理长任务和并发，会把第一期从 1.5 天拖到 3 天。
   但如果你的主要诉求就是"点一下重跑"，那就把 P4 提前。

2. **控制台要不要覆盖内容运营主系统？**
   我建议不要（理由见第 6 节）。但如果你后面打算把图文和视频两条线合并，
   那第一期的数据层就要按"两条线共存"来设计，成本会高一些。

3. **视频脚本要不要做成可在线编辑？**
   现在脚本是 `specs/video_scripts/*.json` 手写。
   做成在线编辑（改旁白/换 layout/调时长 → 保存 → 重跑）价值很高，
   但它属于写操作，取决于第 1 条怎么定。
